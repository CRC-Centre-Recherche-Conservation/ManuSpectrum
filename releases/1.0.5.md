# ManuSpectrum 1.0.5 release notes

ManuSpectrum 1.0.5 changes how the server logs are kept for one year. The hosting provider's TSM has no archive copy
group, so the daily archive of 1.0.4 could not run and `LogArchiveStale` fired. The logs now follow the provider's own
model: about one month on the host, one year in the provider's TSM backup. No migration, no data step; this is not a
security release. The update needs the Ansible playbook first (« Upgrading »).

## Logs

- The host keeps about one month: nginx access and error logs 30 days (was 365), the systemd journal 30 days, at most
  2 GB (was 1 year, 12 GB), `auth.log`, `syslog`, `kern.log`, `ufw.log` and `fail2ban.log`, `wtmp` and `btmp` weekly,
  4 rotations (was 52 weeks and 12 months). A rule missing from the host is skipped.
- The `host` role writes two include lines in the provider's include file (`/var/spool/tsm/etc/inclexcl.def`):
  `include /var/log/.../* LOG_ROTATED_FILES_MG` and the same for the nginx log directory. The provider's daily backup
  (06:25) then keeps one version of each log file and a file deleted from the host 365 days; the VM cannot delete
  backups. Each log exists at least one year and at most about thirteen months, with the client IP unaltered.
- The role refuses to run when `/etc/logrotate.conf` has no `dateext`: the class keeps one version per file name, so
  rotated logs must carry dated names (the provider's host sets it).
- The shorter retention is applied only when the include lines are in place and the provider's last report shows a
  successful backup written at least an hour after them: the first Ansible run writes the lines and leaves the retention
  unchanged (it says so), the next run after that backup applies it. A run limited to the `app` role obeys the same
  rule. A host without the provider's files gets the retention at once.
- A daily timer (`manuspectrum-tsm-check.timer`, 07:30, root) replaces the archive timer. It never calls `dsmc`: it
  reads the provider's report (`/var/spool/tsm/log/dsmc.incremental.local.log`), checks it is from today and that
  `/data` and `/var/log` finished, and checks the include lines are still in the include file. Where the provider's TSM
  client is not configured it writes `manuspectrum_tsm_check_enabled 0` and succeeds.
- Two new warnings read it, `TsmBackupStale` (no successful backup for two days) and `TsmLogIncludeMissing` (the include
  lines are gone); `LogArchiveStale` is removed (`deploy/runbooks/backup.md`).
- The privacy page states the new retention: logs about one month on the server, then one year in the hosting
  provider's backup.
- `deploy/BACKUP.md` « Logs » describes the binding, its limits (after a month the TSM copy is the only copy; the class
  keeps one version, so a log overwritten in place is copied as overwritten by the next backup; TSM is in the same
  computing centre) and how to read an old log (`dsmc query backup -inactive`, `dsmc restore -inactive -pick`, into a
  directory outside the backup domain).

## Backups

- A guard checks the restic repository before the hosting provider's nightly TSM copy
  (`deploy/BACKUP.md`, « The repository guard »): every file named by its SHA-256 must still have it, and `config` must
  equal the recorded reference. The daily pass reads the files changed since the previous one, a full pass runs every
  3 days. On an alteration the provider's job stops before its copy of every filespace, so the good versions TSM holds
  are not replaced; a guard that cannot judge never stops the copy.
- Two warnings read it, `ResticRepoAltered` and `ResticRepoGuardStale`; a critical backup alert does not hide them. The
  `host` role installs the guard and the one line that calls it only on a host with the provider's job.
- The incident guide (`deploy/INCIDENT.md`, « Suspected compromise ») starts with « Protect the backups first »: it
  disables the backup and restore-test timers, cancels a planned update, suspends the provider's job, says what to ask
  the provider and which alerts to silence, and gives the reverse once the incident is closed.

## Upgrading

On a host backed up by the provider's TSM:

1. Before: `sudo grep -n dateext /etc/logrotate.conf` shows an uncommented `dateext`.
2. Run Ansible from a laptop checkout at `v1.0.5`, outside 06:00–08:00 (the provider's job and the check). It writes the
   include lines, installs the check, removes the archive job, and leaves the log retention unchanged (it says so).
3. The next day, after 06:25: `sudo grep -a -E "objects rebound|objects failed" /var/spool/tsm/log/dsmc.incremental.local.log`
   shows a rebound count above 0 and `objects failed: 0`, and `sudo dsmc query backup "/var/log/auth.log*"` shows the
   class `LOG_ROTATED_FILES_MG`.
4. Run Ansible again: the retention is applied (journald restarts; Docker and the containers do not).
5. `sudo manuspectrum-update` at any time after step 2 (`deploy/ADMIN.md`, « Updating the application »).

The same Ansible run installs the backup guard on a host with the provider's job. The next morning
`sudo journalctl -t restic-repo-guard --since today` or the metric
`manuspectrum_restic_repo_guard_last_success_timestamp_seconds` shows that it ran.

Also:

- On a host without TSM, one Ansible run does everything.
- `LogArchiveStale` resolves once Ansible has removed the archive metrics; lift the silence if one was set.
- Logs older than a month at the switch are deleted from the host and kept one more year in TSM (a one-time overshoot
  of the thirteen months).
- Delete `/var/log/manuspectrum-before-1.0.4` a month after the update (TSM keeps it a year).
