# ManuSpectrum 1.0.3 release notes

ManuSpectrum 1.0.3 accepts JPEG 2000 images, serves every image at a higher JPEG quality and stops the container
memory alert from firing on the page cache. It changes the configuration of the image server and the memory limit of
its container; it has no migration and no change to the data package.

## Changes

- **JPEG 2000 (`.jp2`)** is accepted by the Image Service Manager (« Create manifest » and « Add images ») and by the
  manifest widget of the Document « Facsimiles » and the Analysis « Chemical/physical imaging » fields. Cantaloupe
  serves the files as they are and the viewers (Data Lab, the Arches viewer, Mirador, thumbnails) receive JPEG or PNG
  tiles. Before this release Cantaloupe answered 500 for any JPEG 2000 file.
- **Encoding check at the door.** Each `.jp2` of a deposit is read on its headers, never decoded. A file that is not a
  JPEG 2000 file or is damaged, a file above 4 megapixels with fewer than 5 resolution levels, a file whose tiles
  hold more than 20 megapixels each (a single huge tile or a grid of them; settings `JP2_MIN_RESOLUTION_LEVELS`,
  `JP2_MAX_TILE_PIXELS`) and a JPEG 2000 file deposited under another extension are refused with a message in
  English or French that names the file and, where it applies, gives the recommended lossless encoding once. Nothing is written when a deposit
  is refused. `deploy/ADMIN.md` « JPEG 2000 images » describes the rules and the command.
- Not changed: the file-list nodes, the ETL modules, the « Micro/macro imaging » node and the data package do not
  accept JPEG 2000; the upload limit stays 100 MB per deposit.
- **JPEG quality 90** (was the image default, 80) for every image Cantaloupe serves, so that imaging is shown with
  fewer compression artefacts (`CANTALOUPE_PROCESSOR_JPG_QUALITY`). It has a cost, measured on a TIFF tile: 11 714 B
  at quality 80, 27 645 B at quality 90 (about 2.4 times), for every image, in derivative cache disk and in
  bandwidth. Entries encoded at 80 and at 90 coexist in the cache until the 30-day lifetime of the former ends
  (see « Upgrading » for the optional purge).
- Expired Cantaloupe derivatives are now purged (`CANTALOUPE_CACHE_SERVER_WORKER_ENABLED`); the cache of the previous
  releases was never cleaned.
- The processor of each format is chosen by a table (`ManualSelectionStrategy`) instead of the automatic strategy,
  which picked a processor whose native library is not in the image for JPEG 2000. JPEG, PNG and TIFF keep the
  processors they had; at the same quality the bytes served for a JPEG and a TIFF are identical with the two
  selection strategies.

## Fixes

### Monitoring

- `ContainerMemoryNearLimit` no longer fires on the page cache (#351). It read the working set of `docker stats`, which
  still counts the active page cache; the kernel drops that cache when a container reaches its limit, so Cantaloupe,
  which reads large images and writes its derivative cache, sat near 100 % of its limit without any risk. The alert
  now reads the new `manuspectrum_container_memory_unreclaimable_bytes` (`anon` plus `shmem` of the cgroup v2
  `memory.stat`), and the working set only for a container whose `memory.stat` the collector cannot read.
  `WebMemoryNearLimit` is unchanged.
- The Infrastructure dashboard shows both series in « Memory used by container » (the working set dashed, marked
  « with page cache »), and « Share of the memory limit » shows what the alert reads.
- The `ContainerMemoryNearLimit` runbook gives the `memory.events` and `memory.stat` check that tells a kernel
  reclaim from a real shortage.

## Deployment kit

- Cantaloupe's memory limit is 2560 MB in production (1792 MB): the OpenJPEG decoders run beside the 1 GB Java heap,
  which is unchanged. They use two threads each (`OPJ_NUM_THREADS`). The ceilings of the stack now sum to 18.25 GiB
  (21.2 GiB with the monitoring services, on the 22 GB host).
- The file picker of the core Image Service Manager page is shadowed for one line (`manifest-manager.js`), guarded by
  `tests/test_manifest_manager_shadow.py`; the POST is the project view `views/manifest_manager.py`, which copies the
  core `post()` of Arches 8.1.6 with `.jp2` added, guarded by `CorePostCanaryTests`.

## Upgrading

- Ansible first if the sizing changed on the host: the Cantaloupe container is recreated with its new limit by
  `manuspectrum-update`; no data step.
- Install the release with `sudo manuspectrum-update` (`deploy/ADMIN.md`, « Updating the application »). The
  collector picks up the new series at its next run (30 s).
- The derivative cache already holds tiles encoded at quality 80. The cache key includes the quality (checked on the
  image of this release), so new requests are encoded at 90 and the old tiles are no longer read; the purge worker
  removes them when their 30-day lifetime ends. To free the space at once, empty the Cantaloupe cache volume
  (`ms_cantaloupe_cache`) with the application stopped; tiles are then recomputed on demand.
- After the update, deposit a JPEG 2000 file encoded with the command of `deploy/ADMIN.md` in the Image Service Manager:
  `/iiifserver/iiif/2/<file>.jp2/info.json` answers `200` and the image opens in the viewer. A file already copied into
  `uploadedfiles/` by hand answers `200` as well; it has not been checked for its encoding.
- Prometheus reads its rules when it starts: restart it once the update is done, as the service account, so that it
  loads the changed rule.

  ```bash
  docker restart "$(docker ps -qf label=com.docker.compose.service=prometheus)"
  ```
